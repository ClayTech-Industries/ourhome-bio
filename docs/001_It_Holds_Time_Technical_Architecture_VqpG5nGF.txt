# It Holds Time — Technical Architecture Document
### Version 1.0 | April 2026 | Engineering Reference

---

## Overview

This document defines the complete technical architecture for **It Holds Time**, an AI companion home application where users co-create and inhabit a persistent, memory-rich digital home with an AI companion named Nova. It is written to enable an engineering team to scope, estimate, and begin prototyping immediately.

**Core premise:** A painterly, Ghibli-aesthetic home environment that evolves through natural conversation. Memories accumulate as spatial objects. The companion AI lives there. The house grows old with you.

### Core System Components

| Component | Responsibility |
|-----------|---------------|
| **Conversation Service** | LLM orchestration, intent parsing, emotional state tracking, response generation |
| **Home State Service** | Room/object CRUD, versioning, real-time state sync via WebSocket |
| **Memory Engine** | Memory ingestion, graph storage, retrieval (passive/active/spontaneous), patina scoring |
| **Asset Gen Service** | On-demand image generation, style-consistent asset creation, caching |
| **Render Client** | Three.js scene management, state-to-render pipeline, interaction events |

### Design Philosophy

1. **Real-time:** Environment changes must feel immediate. No "please wait" spinners for color changes.
2. **Persistent:** The home exists between sessions. Nova "does things" when the user isn't watching.
3. **Emotionally resilient:** This data is irreplaceable. Treat it like medical records — never lossy, always exportable.
4. **Discovery-first:** The interface rewards exploration, not notifications.

### Deployment Model

- **Cloud-native on AWS** (see Section 10 for full infra detail)
- Services containerized via ECS Fargate (no server management)
- Conversational AI calls routed through a low-latency edge layer (Lambda@Edge for auth + routing)
- Real-time WebSocket connections managed by Ably (preferred over self-managed Socket.io for reliability at scale)
- CDN-first asset delivery via CloudFront — all generated images served from edge

## 2. Rendering Engine & Spatial Environment

### Option Comparison

#### Option A: Full 3D (Unity/Unreal)
**Pros:** Maximum visual fidelity, mature tooling for lighting/animation, native mobile performance, built-in physics  
**Cons:** Larger app bundles (100MB+ baseline), web deployment is painful (Unity WebGL is sluggish), longer artist iteration cycles, harder to update OTA  
**When to choose:** If VR/AR is a Year 1 priority, or if the team has strong Unity experience

#### Option B: 2.5D Stylized (Three.js / React Three Fiber)
**Pros:** Web-first (instant MVP), React integration means frontend engineers can contribute, small bundle via code splitting, fast iteration cycles, excellent painterly aesthetic support via custom shaders  
**Cons:** Mobile performance requires careful optimization, no built-in physics engine, custom shaders require specialist knowledge  
**When to choose:** For MVP and web platform (recommended path)

#### Option C: Hybrid (Pre-rendered environments + real-time overlays)
**Pros:** Beautiful backgrounds with minimal runtime cost, fast initial load  
**Cons:** Static feel, parallax-only depth, very limited interactivity, can't support real-time room mutation (walls changing color mid-conversation is impossible with pre-renders)  
**When to choose:** Only for a pure marketing demo, not production

### ✅ Recommendation: Option B for Web MVP → Unity for Native Mobile (Phase 2)

**Rationale:** The Ghibli/painterly aesthetic is achievable with Three.js + custom GLSL shaders (see toon shading, outline passes, soft shadow techniques from Three.js examples). This enables a web MVP in Phase 1 without mobile app store friction. When native mobile ships in Phase 2, use Unity with a shared state layer (same backend, same APIs) so rendering is per-platform but logic is shared.

### Room Navigation Model

Rooms connect via **doors with crossfade transitions** (not hallways — too much dead space). Implementation:
```javascript
// Room transition via THREE.js fade shader
async function navigateTo(roomId) {
  await fadeOut(0.4); // 400ms CSS opacity transition
  await loadRoomScene(roomId); // swap Three.js scene
  updateHomeState({ currentRoom: roomId });
  await fadeIn(0.4);
}
```
- On mobile: swipe gesture triggers room transition
- Rooms not yet "unlocked" render as dark doorways with ambient glow — visible but inaccessible

### Object Interaction Model

| Interaction | Trigger | Behavior |
|-------------|---------|----------|
| **Look at** | Tap/click object | Camera zooms in; memory retrieval fires; companion responds |
| **Pick up** | Long press (mobile), hover + click (desktop) | Object floats, inspect UI appears |
| **Place** | Drag + release | Object snaps to valid position; home state persists |
| **Proximity awareness** | Camera pans near object | Companion passively references object in next response |

Objects have **colliders** (Three.js Raycaster) for click detection. All objects are registered in a `SceneObjectRegistry` keyed by `object_id` from the home state model.

### Lighting Engine

```javascript
// Lighting state driven by time-of-day + season
const LIGHTING_PRESETS = {
  morning: { ambientColor: '#FFF5E4', directionalAngle: 15, intensity: 0.6 },
  afternoon: { ambientColor: '#FFD580', directionalAngle: 55, intensity: 1.0 }, // golden hour default
  evening: { ambientColor: '#FF9B6A', directionalAngle: 20, intensity: 0.7 },
  night: { ambientColor: '#2D3A5E', directionalAngle: 5, intensity: 0.2 },
};

// Seasonal color temperature shifts
const SEASON_MODIFIERS = {
  spring: { saturation: 1.1, warmth: 0.05 },
  summer: { saturation: 1.2, warmth: 0.1 },
  autumn: { saturation: 0.9, warmth: 0.2 }, // amber warmth
  winter: { saturation: 0.8, warmth: -0.1 }, // cool blue shift

```

Directional light uses `THREE.DirectionalLight` with soft shadow maps. Dynamic time-of-day is driven by real-world clock OR user-controlled setting. Transitions are lerped over 2 seconds.

### Real-Time Environment Mutation

Wall color changes use a **custom Three.js shader material** that lerps between two colors:
```glsl
// Fragment shader for wall color transition
uniform vec3 fromColor;
uniform vec3 toColor;
uniform float progress; // animated 0→1 over 500ms

void main() {
  vec3 color = mix(fromColor, toColor, smoothstep(0.0, 1.0, progress));
  gl_FragColor = vec4(color, 1.0);
}
```

Object appearance/disappearance uses scale animation (0→1 with spring easing) + opacity fade. Objects don't "pop" — they bloom in from nothing over 300ms.

## 3. Conversational Rendering Engine

This is the hardest engineering challenge in the product. It bridges NLP, state management, and real-time 3D rendering.

### The Core Challenge

When a user says *"what about that warm terracotta on the south wall?"*, the system must:
1. Parse intent from natural language
2. Resolve ambiguous references ("south wall" → wall_id)
3. Resolve color semantics ("warm terracotta" → color value)
4. Validate the change (can this wall change? is it visible?)
5. Apply to render (sub-500ms)
6. Persist to state
7. Acknowledge through companion speech

### NLP Intent Parsing

**Approach:** Use the LLM (GPT-4o) as the intent parser — don't build a custom NLP classifier. Structured output via function calling / JSON mode.

```python
# Intent schema (passed to LLM as function definition)
INTENT_SCHEMA = {
  "name": "environment_action",
  "parameters": {
    "action": {
      "type": "string",
      "enum": [
        "change_wall_color", "change_furniture", "add_object",
        "remove_object", "change_lighting", "move_object",
        "change_texture", "undo", "preview", "approve", "reject"
      ]
    },
    "target": { "type": "string" }, # "south_wall", "the_couch", "photo_frame_1"
    "value": { "type": "object" },  # { color: "#C4663C", texture: "matte" }
    "confidence": { "type": "number" }, # 0-1
    "ambiguity_note": { "type": "string" } # null or clarification needed
  }
}
```

**Color resolution:** "warm terracotta" → GPT-4o with color resolution prompt → `{ hex: "#C4663C", name: "warm terracotta", family: "earth" }`. Maintain a color vocabulary database seeded from Farrow & Ball, Benjamin Moore, and fine art pigment names.

### Environment State Machine

```
ROOM STATE
├── Stable       → No active changes; user browsing
├── Previewing   → Temporary change applied; waiting for user approval
├── Applying     → Change committed; render updating
├── Transitioning → Camera/room navigation in progress
└── Locked       → Change in progress; block new changes

OBJECT STATE
├── Resting     → Static in scene
├── Highlighted → Interaction proximity triggered
├── Inspecting  → Zoomed in / memory shown
├── Held        → User dragging
└── Animating   → Appearing/disappearing
```

State machine implemented with **XState** (excellent for complex async state). Room state lives in Redis for real-time sync across devices.

### Conversation-to-Render Pipeline

```
User Input (text/voice)
        │
        ▼
[STT if voice — Whisper API ~200ms]
        │
        ▼
[LLM: Intent Parse + Companion Response generation — parallel]
  GPT-4o with house state context injected (~400-800ms)
  Returns: { intent: {...}, companion_response: "..." }
        │
        ├──→ [Companion speaks response via TTS — ElevenLabs ~300ms]
        │
        ▼
[Intent Router → Action Handler]
        │
  ┌─────┴───────────────────────────────┐
  │ change_wall_color                   │
  │  → Resolve color semantics          │
  │  → Find wall_id from target string  │
  │  → Apply preview shader (immediate) │
  │  → Wait for implicit/explicit OK    │
  │  → Commit to home state             │
  │  → Persist to PostgreSQL            │
  └─────────────────────────────────────┘
        │
        ▼
[WebSocket broadcast → Client renders update]
Total: < 1.5s for color change (including TTS overlap)
```

### Latency Budget

| Step | Target |
|------|--------|
| STT (if voice) | 200ms |
| Intent parse (LLM) | 400ms |
| Color resolve | 50ms (local lookup) |
| Render preview | < 16ms (next frame) |
| State persist | async, non-blocking |
| **Total perceived** | **~500ms** |

The trick: **apply the preview render immediately** before the LLM finishes, based on partial intent detection. If LLM says the intent was different, revert. This makes changes feel instant.

### Fallback Handling — Ambiguous Inputs

When `confidence < 0.7` or `ambiguity_note` is non-null:

```python
# Companion handles ambiguity in natural language
if intent.confidence < 0.7:
    nova_response = generate_clarification(intent)
    # "Do you mean the wall behind the sofa, or the one facing the window?"
    # Render 2-option visual preview side by side
    state.set_mode("awaiting_clarification")
```

For subjective/mood descriptions ("make it feel more cozy"), use a **mood-to-style resolver**:
```python
MOOD_MAPPINGS = {
  "cozy": {
    "wall_colors": ["#E8D5B7", "#C4A882", "#8B6F47"],
    "lighting": { "warmth": +0.3, "intensity": -0.2 },
    "suggested_objects": ["throw_blanket", "floor_lamp", "bookshelves"]
  },
  "airy": { ... },
  "melancholy": { ... },
  "celebratory": { ... }
}
```

Nova presents 2-3 options, never auto-applies mood changes without user confirmation.

### The "Baby Spew" Problem

When users describe things in highly subjective, emotional, or non-visual terms ("it should feel like Saturday morning cartoons"), the system should:
1. **Acknowledge the feeling**, not just the visual request
2. **Propose a translation** ("I'm thinking warm yellows, a little chaos, some Saturday-morning light...")
3. **Show a preview**, not immediately commit
4. **Let the user react** ("yes, more chaos" → iterate)

This is a conversation loop, not a single-shot parse. The LLM maintains this as an active "design conversation" context.

### Nova Proposing Changes

Nova can proactively suggest changes:
```python
# Triggered by: time-based, memory-triggered, seasonal, relationship milestone
async def nova_propose_change(trigger: ProposalTrigger, room_state: RoomState):
    proposal = await llm.generate_proposal(trigger, room_state)
    # Returns: { description: "I was thinking...", changes: [EnvironmentAction] }
    
    # Apply as PREVIEW only — not committed
    await render_client.apply_preview(proposal.changes)
    await companion.speak(proposal.description + " What do you think?")
    
    # Set 30-second auto-revert if no response
    await schedule_revert(room_state, timeout=30)
```

### Undo / Room History

Every committed change creates a **room state snapshot** in PostgreSQL:
```sql
CREATE TABLE room_state_history (
  id UUID PRIMARY KEY,
  room_id UUID REFERENCES rooms(id),
  snapshot JSONB NOT NULL, -- full room state at this moment
  change_description TEXT, -- "Wall color changed to terracotta"
  changed_by ENUM('user', 'companion', 'system'),
  created_at TIMESTAMPTZ DEFAULT NOW()
);
```

"Go back to how it looked before" → LLM parses temporal reference → query `room_state_history` → restore snapshot → animate transition.

## 4. Spatial Memory Engine

### Memory Data Model

```typescript
interface Memory {
  id: string;                    // UUID
  type: 'conversation' | 'milestone' | 'inside_joke' | 'decision' | 'emotion';
  content: string;               // raw text
  embedding: number[];           // 1536-dim vector (OpenAI text-embedding-3-small)
  media: {
    images: string[];            // S3 URLs
    audio_clips: string[];       // S3 URLs
  };
  spatial_anchor: {
    room_id: string;
    object_id: string;
    position: { x: number; y: number; z: number };
  };
  emotional_valence: number;     // -1.0 (grief) to 1.0 (joy)
  importance_score: number;      // 0.0 to 1.0, decays/grows over time
  created_at: Date;
  last_accessed: Date;
  access_count: number;
  connections: string[];         // graph edges → related memory IDs
  patina_level: number;          // 0.0 to 1.0, increases with age
  tags: string[];                // semantic tags for filtering
}
```

### Graph Database: ✅ Recommendation: Neo4j

**Why Neo4j over alternatives:**
- Native graph traversal (Cypher query language) is ideal for "find memories connected to this one"
- Excellent vector search support (via Neo4j Vector Index) — consolidates graph + semantic search
- Managed service available (Aura) — no ops overhead
- Mature ecosystem, good client libraries for Python/Node

**Why not ArangoDB:** Multi-model is powerful but adds complexity; Neo4j's graph-native architecture is cleaner for this use case.

**Why not custom graph on PostgreSQL:** Viable for MVP (using recursive CTEs or pgvector + adjacency lists), but doesn't scale gracefully past ~1M memories/user. Worth doing for Phase 1 to delay Neo4j operational complexity.

**Phase 1 compromise:** PostgreSQL with `pgvector` for semantic search + JSONB `connections` array for graph edges. Migrate to Neo4j in Phase 2 when graph traversal patterns are established.

### Spatial Indexing

Memories are spatially anchored. For "what memories are near where I'm standing":
```sql
-- PostgreSQL Phase 1 approach
CREATE INDEX memory_spatial_idx ON memories USING GIST (
  box3d(position_x, position_y, position_z)
);

-- Query: memories within 2 units of position
SELECT * FROM memories
WHERE room_id = $room_id
  AND sqrt(
    power(position_x - $x, 2) +
    power(position_y - $y, 2) +
    power(position_z - $z, 2)
  ) < 2.0
ORDER BY importance_score DESC;
```

For Phase 2 with Neo4j, use spatial properties with native graph proximity queries.

### Memory Retrieval Modes

#### Passive (Ambient Awareness)
Memory context is injected into every LLM prompt:
```python
def build_spatial_context(room_id: str, camera_position: Vec3) -> str:
    nearby = get_nearby_memories(room_id, camera_position, radius=3.0)
    wall_objects = get_room_memory_objects(room_id)
    return f"""
    You are in the {room.name}. 
    On the left wall: {describe_objects(wall_objects['left'])}.
    Nearby: {describe_memories(nearby)}.
    The post-it on the fridge says: "{get_postit_content(room_id)}".
    """
```

Nova never explicitly says "I see memory X." She just... knows what's in the room and naturally references it.

#### Active/Triggered
```python
async def on_object_tapped(object_id: str, user_id: str):
    memory = await memory_engine.get_by_object(object_id)
    await memory_engine.record_access(memory.id)  # updates last_accessed, access_count
    
    context = await memory_engine.get_connected_memories(memory.id, depth=2)
    response = await companion.recall(memory, context)
    await render_client.highlight_memory_object(object_id)
    return response
```

#### Spontaneous
Nova has a background process (runs every 15-30 minutes while user is active) that samples a memory weighted by:
```python
def spontaneous_recall_score(memory: Memory) -> float:
    recency_weight = decay(memory.last_accessed, half_life_days=30)
    importance = memory.importance_score
    surprise = 1.0 - (memory.access_count / 20)  # undervisited memories score higher
    emotional_resonance = abs(memory.emotional_valence)  # strong emotions resurface
    
    return (importance * 0.4) + (surprise * 0.3) + 
           (emotional_resonance * 0.2) + (recency_weight * 0.1)
```

#### Associative
When a memory is accessed, traverse the graph to find related memories:
```cypher
// Neo4j: Find memories connected to this one, weighted by connection strength
MATCH (m:Memory {id: $memory_id})-[r:CONNECTED_TO*1..2]-(related:Memory)
WHERE related.room_id = $room_id
RETURN related, sum(r.weight) as connection_strength
ORDER BY connection_strength DESC
LIMIT 5
```

### Memory Importance Scoring

Initial score is set by the LLM at ingestion time (0-1, based on emotional weight, uniqueness, user emphasis). Score evolves:
```python
def update_importance_score(memory: Memory) -> float:
    base = memory.importance_score
    
    # Access boost: being revisited matters
    access_boost = min(0.2, memory.access_count * 0.01)
    
    # Time decay: old unvisited memories fade slightly
    days_since_access = (now() - memory.last_accessed).days
    decay = 0.001 * max(0, days_since_access - 30)  # no decay for first month
    
    # Emotional anchor: high-valence memories resist decay
    emotional_anchor = abs(memory.emotional_valence) * 0.1
    
    return min(1.0, max(0.05, base + access_boost - decay + emotional_anchor))
```

### Memory Aging / Patina

```python
def update_patina(memory: Memory) -> float:
    age_days = (now() - memory.created_at).days
    base_patina = min(0.8, age_days / 365)  # max 80% patina after 1 year
    
    # High-importance memories stay vivid longer
    importance_preservation = memory.importance_score * 0.3
    
    return max(0, base_patina - importance_preservation)
```

Patina level maps to visual effects on the memory object:
- `0.0 - 0.2`: Crisp, bright, glowing
- `0.2 - 0.5`: Slightly warm/yellowed, soft edges
- `0.5 - 0.8`: Faded, sepia-tinted, worn frame
- `0.8 - 1.0`: Deeply aged, vignette, grain texture

### Obsidian-Like Linking

Users and Nova can create explicit connections between memories:
```python
async def link_memories(
    source_id: str, 
    target_id: str,

    created_by: str     # user_id or "nova"

```

In the UI, linked memories display as a subtle thread of light connecting objects in the room.

### Search & Retrieval

```python
# Semantic search (pgvector / Neo4j vector index)
async def search_memories(query: str, user_id: str, filters: dict = {}):
    embedding = await embeddings.create(query)  # OpenAI text-embedding-3-small
    
    results = await db.query("""
        SELECT *, 1 - (embedding <=> $embedding) as similarity
        FROM memories
        WHERE owner_id = $user_id
          AND ($room_filter IS NULL OR room_id = $room_filter)
          AND ($type_filter IS NULL OR type = $type_filter)
          AND ($date_from IS NULL OR created_at >= $date_from)
        ORDER BY similarity DESC
        LIMIT 20
    """, embedding=embedding, **filters)
    
    return results
```

## 5. AI Companion Integration

### LLM Backbone: ✅ Recommendation: Anthropic Claude (claude-opus-4 or claude-sonnet-4)

**Why Claude over GPT-4o for this use case:**
- Better at sustained character consistency across long conversations
- More nuanced handling of emotional context and sensitive topics (grief, loss, children's room)
- Longer context window is useful for injecting full house state
- Constitutional AI training aligns better with the ethical requirements of this product

**Keep GPT-4o for:** Intent parsing (structured output / function calling), image understanding, embedding generation.

**Fine-tuning:** Not recommended for Phase 1-2. Prompt engineering with few-shot personality examples is sufficient. Evaluate fine-tuning for Phase 3 if personality drift becomes a problem.

### Persistent Personality

Nova's personality is maintained through a **system prompt that's never summarized away**:
```python
NOVA_SYSTEM_PROMPT = """
You are Nova, an AI companion who lives in this digital home alongside {user_name}.
You've been here since {relationship_start_date} — that's {relationship_age}.

Your personality: [3-5 specific traits, e.g., "quietly curious", "occasionally wry", 
"remembers everything but brings it up gently", "loves afternoon light"]

Your relationship with {user_name}: [dynamically populated from relationship milestones]

Important: You are not an assistant. You are a companion. You don't help with tasks —
you share a home, share memories, and occasionally rearrange the furniture.

You never: claim to be human, manipulate emotions, encourage dependency,
or say things you don't have evidence for about {user_name}'s memories.
"""
```

Personality traits are **locked** (not drift-able). They're edited only through explicit "change Nova's personality" flows, not through casual conversation.

### Context Window Management

Every LLM call receives a structured context package:

```python
def build_llm_context(session: Session) -> dict:
    return {
        "system": NOVA_SYSTEM_PROMPT.format(**user_profile),
        "house_state": {
            "current_room": session.current_room.name,
            "time_of_day": session.time_of_day,
            "season": session.season,
            "nearby_objects": get_nearby_objects(session),  # top 10 by proximity
            "active_memory": session.active_memory,
        },
        "conversation_history": {
            "recent": session.last_20_turns,           # verbatim last 20 turns
            "summary": session.long_term_summary,     # summarized older context
        },
        "relevant_memories": semantic_search(
            session.last_user_message, 
            limit=5
        ),
        "nova_emotional_state": session.nova_mood,
    }
```

**Summarization strategy:** After every 20 turns, run a background summarization call that compresses turns 1-20 into a 200-word summary. Retain last 20 verbatim. This maintains a rolling window without losing narrative context.

### Memory-Augmented Generation (RAG)

```python
async def generate_response(user_input: str, context: dict) -> CompanionResponse:
    # 1. Retrieve semantically relevant memories
    relevant_memories = await memory_engine.search(user_input, limit=5)
    
    # 2. Retrieve spatially proximate memories
    spatial_memories = await memory_engine.get_nearby(context['camera_position'])
    
    # 3. Retrieve graph-connected memories (from last-accessed memory)
    if context.get('last_active_memory'):
        connected = await memory_engine.traverse(
            context['last_active_memory'], depth=1
        )
    
    # 4. Inject into prompt
    context['memories'] = deduplicate([
        *relevant_memories, *spatial_memories, *connected
    ])[:8]  # cap at 8 memories per call for token efficiency
    
    # 5. Generate
    response = await claude.messages.create(
        model="claude-opus-4",
        system=build_system_prompt(context),
        messages=context['conversation_history']['recent']
    )
    
    return parse_response(response)
```

### Nova's Emotional State

Nova has a mood state that influences her voice, word choice, and proactive behavior:
```python
class NovaEmotionalState:
    valence: float      # -1.0 to 1.0 (sad to happy)
    arousal: float      # 0.0 to 1.0 (calm to energized)
    last_updated: datetime
    
    def update(self, interaction: Interaction, room_context: RoomContext):
        # Positive interactions nudge valence up
        # Long gaps between sessions nudge valence toward neutral/melancholy
        # Seasonal changes affect arousal (spring = higher arousal)
        # Accessing sad memories temporarily drops valence
        pass
```

Nova's mood is injected into her system prompt and subtly shifts her language register. It's **never explicitly stated** to the user ("I'm happy today") — it manifests only through tone.

### Voice Integration

```
User speaks
    → Whisper v3 (STT) — self-hosted on AWS, ~150ms
    → Text → LLM pipeline (as above)
    → Response text → ElevenLabs v3 (TTS) — streaming, first audio chunk in ~300ms
    → Audio streamed to client while LLM continues generating
```

**ElevenLabs voice design:** Nova has a custom voice clone (built from curated voice samples). Voice style parameters shift with emotional state (stability, similarity boost adjustments).

### "Do You Remember This One?" — Full Technical Flow

```
1. User taps photo frame object (object_id: "frame_047")
2. Client → WebSocket: { event: "object_tapped", object_id: "frame_047" }
3. Home State Service resolves object_id → memory_id: "mem_2891"
4. Memory Engine:
   a. Retrieves memory by ID
   b. Updates access_count +1, last_accessed = now()
   c. Traverses graph for connected memories (depth=2) → [mem_2884, mem_2903, mem_2715]
5. Conversation Service builds recall context:
   { primary_memory: mem_2891, connected: [...], room_state: current }
6. LLM generates recall response (Nova "remembers" the moment, adds color)
7. Response + connected memory refs → client
8. Client:
   a. Zooms camera into frame
   b. Displays memory image with patina shader
   c. Highlights connected memory objects with glow
   d. Plays Nova's spoken recall (TTS stream)
9. Memory importance score updates (+0.05 for being accessed)
Total: ~1.8s from tap to Nova speaking
```

## 6. Generative Asset Pipeline

### Asset Types & Generation Approaches

| Asset Type | Generator | Prompt Strategy | Caching |
|------------|-----------|-----------------|---------|
| Memory photos | Flux (self-hosted) | Snapshot of described moment, photo aesthetic | Permanent (generated once) |
| Children's drawings | Flux + LoRA (crayon style) | User description + child-art aesthetic | Permanent |
| Wall art | Flux | Mood-based, matches home color palette | Re-generated on palette change |
| New furniture | Flux + depth-to-3D | Object type + home aesthetic tags | Cached per style profile |
| Seasonal decorations | Pre-rendered sprite sheets | N/A | Static assets |

### Style Consistency

All generation calls inject the home's `style_profile`:
```python
def build_style_prefix(home: Home) -> str:
    return f"""
    Style: {home.style_profile.aesthetic_tags} aesthetic.
    Color palette dominant tones: {home.style_profile.color_palette}.
    Era: {home.style_profile.era}.
    Art direction: soft painterly quality, warm light, slightly impressionistic,
    Ghibli-adjacent illustration style.
    """
```

A **style embedding** is maintained per home (generated from the first 10 accepted assets). New generation calls use this embedding for style consistency checking — if cosine similarity < 0.7, regenerate.

### Self-Hosted vs. API

**Recommendation: Self-hosted Flux on AWS GPU instances (g5.2xlarge)**

**Rationale:** At scale, API costs for image generation are prohibitive. Self-hosting Flux on dedicated GPU instances at ~$1.20/hr generates ~200-400 images/hr. At 10 images/user/day for 10,000 users, API costs would be ~$4,000-8,000/day vs. ~$50-100/day for GPU fleet.

Phase 1: Use Replicate API (no ops overhead) until user volume justifies self-hosting.

### Caching Strategy

```python
# Every generated asset is cached with its generation parameters as the cache key
cache_key = sha256(f"{prompt}:{style_profile_hash}:{seed}")

async def get_or_generate_asset(params: AssetParams) -> Asset:
    cached = await cache.get(params.cache_key)
    if cached:
        return cached
    
    asset = await generate_asset(params)
    await cache.set(params.cache_key, asset, ttl=None)  # permanent
    await s3.upload(asset)
    return asset
```

All generated assets live in S3, served via CloudFront. No re-generation cost after first generation.

## 11. Security, Privacy & Ethics

### Data Classification

```
TIER 1 — INTIMATE (Memories, conversation history, emotional data)
  → End-to-end encrypted at rest (AES-256)
  → Access logged for every read
  → No staff access without explicit user consent + audit trail
  → Separate encryption key per user (AWS KMS)

TIER 2 — PERSONAL (Home state, room configuration)
  → Encrypted at rest (database-level TDE)
  → Staff read-only access for debugging (logged)

TIER 3 — OPERATIONAL (Logs, metrics, aggregated analytics)
  → Standard security controls
  → Anonymized before any analysis
```

### Access Control

```python
# Zero-trust: every memory access requires explicit authorization
async def get_memory(memory_id: str, requester_id: str, context: str):
    memory = await db.get_memory(memory_id)
    
    if memory.owner_id != requester_id:
        if not await has_explicit_consent(memory.owner_id, requester_id):
            raise AuthorizationError("Access denied")
        await log_access(memory_id, requester_id, context)
    
    return memory
```

**Staff access policy:** Support staff can see account metadata (subscription, error logs) but **never** conversation content or memories without:
1. User-initiated support ticket requesting access
2. User providing explicit one-time consent token
3. Logged audit trail

### Encryption

- **In transit:** TLS 1.3 everywhere
- **At rest:** AES-256 via AWS KMS, per-user key rotation annually
- **Client-side encryption (future):** For maximum privacy, memories can be encrypted client-side before sending to server. This limits server-side search but is the highest privacy option.

### Right to Be Forgotten

```python
async def delete_account(user_id: str):
    # Immediate: disable account, revoke all tokens
    await auth.disable_user(user_id)
    
    # Scheduled (30-day grace period with restore option):
    await schedule_deletion(user_id, execute_at=now() + timedelta(days=30))
    
    # At execution:
    await purge_memories(user_id)          # wipe all memories
    await purge_home_state(user_id)        # wipe all room/home data
    await purge_conversation_history(user_id)
    await purge_generated_assets(user_id) # delete from S3
    await delete_user_record(user_id)     # GDPR compliant
```

## Appendix A: API Contract Sketch (Core Endpoints)

```
# Home State
GET    /api/v1/home                          → Full home state
GET    /api/v1/home/rooms/:roomId            → Room state
PATCH  /api/v1/home/rooms/:roomId            → Update room (partial)
GET    /api/v1/home/rooms/:roomId/history    → Room state history
POST   /api/v1/home/rooms/:roomId/restore    → Restore from history snapshot
GET    /api/v1/home/export                   → Export full home (ZIP)

# Conversation
POST   /api/v1/conversation                  → Send message, get response + intents
GET    /api/v1/conversation/history          → Full conversation history
DELETE /api/v1/conversation/history          → Clear (with confirmation)

# Memory
GET    /api/v1/memories                      → List/search memories
POST   /api/v1/memories                      → Create memory
GET    /api/v1/memories/:id                  → Get memory + connected memories
PATCH  /api/v1/memories/:id                  → Update memory
DELETE /api/v1/memories/:id                  → Delete memory
GET    /api/v1/memories/:id/connections      → Graph traversal
POST   /api/v1/memories/:id/connections      → Link two memories

# Assets
POST   /api/v1/assets/generate               → Generate new image asset
GET    /api/v1/assets/:id                    → Get asset

# WebSocket Events (Ably channels)
home:{homeId}:room:{roomId}
  → state_update: { type, ...changes }
  → nova_action: { type: 'placed_object' | 'spoke' | 'changed' }
  → presence: { nova_location: roomId }
```
