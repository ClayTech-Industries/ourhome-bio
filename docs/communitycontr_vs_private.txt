What you’re describing is less “open-source” and more **community-enabled, values-gated building**. You can do that without paying a big team, but you’ll want a structure that:

1) attracts the right contributors/users,  

2) protects the ethos (so it doesn’t get mobbed or forked into something misaligned), and  

3) keeps your costs bounded.

## The model I’d use: “Open community, controlled core”

### Keep the *core product* controlled (private repo)

Core = anything that defines the relationship experience and safety stance:

- companion behavior + memory rules
- privacy model / encryption / export
- children’s room constraints + safety filters
- any “retention loop” decisions (you explicitly don’t want these)

This is where misaligned contributions can do the most damage.

### Invite community contribution in *bounded modules*

Open these as separate repos or clearly separated packages:

- **Renderer sandbox** (Three.js/R3F “room + objects + lighting + transitions”)
- **Home state schema** (JSON schema + TypeScript types + sample data)
- **Asset pipeline tools** (image optimization, stitching walkthrough clips, etc.)
- **Documentation repo** (public “trust model” + design principles)

This lets people contribute meaningfully without needing access to the sensitive heart.

## How to recruit from Reddit/Discord without getting swarmed

The key is: don’t post “help build OurHome.” Post **one tight, specific call**.

### A good “strict but welcoming” intake funnel

1) Public post in the AI companion subreddits/Discords:

- 35s demo
- 5 bullet vision
- link to your published Notion investor/demo page
- link to a **“Contribute / Early Builder” form** (Google Form/Typeform)

2) Form asks for:

- GitHub profile
- what they want to work on (renderer, schema, tooling, etc.)
- time zone + availability
- one short question that reveals values alignment (e.g. “What should this product never do?”)

3) You invite a small cohort into:

- a private Discord channel (or a private GitHub org team)
- a private repo (or issues board) with very clear boundaries

This is how you stay open *to the right people* while avoiding drive-by chaos.

## Protecting against “mob mentality”

A few practical guardrails that work:

- **Code of Conduct** + strict moderation in your Discord (non-negotiable)
- **Contribution rules**: PRs require approval; no direct pushes
- **Scope boundaries**: “No work on companion behavior without explicit request”
- **Decision log**: you keep final say; community can propose

Also: publish your **Trust / Safety stance** early (the page you’re building). It acts like a filter: misaligned people self-select out.

## Keeping cost low (your constraint)

You don’t need “dev teams.” You need:

- 1–2 solid volunteer contributors on the renderer/prototype side
- and you as the product/safety owner

To avoid infra costs early:

- Start with a **web prototype** (Next.js + Three.js) that runs locally
- Defer real-time multi-user + heavy memory graph until you have traction
- Use mocked data and a “recorded demo mode” so people can experience it without a backend

## A concrete phased plan (community-friendly)

**Phase 0 (now):** Notion public demo + Trust/Safety page + contribution form  

**Phase 1:** Open-source renderer sandbox + schema repo (good first issues)  

**Phase 2:** Private core repo MVP (invite-only contributors)  

**Phase 3:** When stable, selectively open more (if you still want to)
